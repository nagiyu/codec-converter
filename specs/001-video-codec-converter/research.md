# ビデオコーデックコンバータに関する調査と決定

この文書は、機能仕様および技術的文脈の「NEEDS CLARIFICATION」項目を解決するための決定事項を記録します。

## 決定 1 — Next.js のバージョンとランタイム

- 決定: サーバーサイド／APIルートには Next.js 13 の App Router と Node.js 18 ランタイムを使用する。デプロイはコンテナイメージとして、AWS Lambda コンテナランタイムをターゲットにする。
- 理由: Next.js 13 の App Router は安定しており、最新のレイアウト、ストリーミング、サーバーコンポーネントに整合するため。Node 18 は Lambda にサポートされ、エコシステムと一致する。
- 検討した代替案: 古い Pages Router — 将来性を考慮して App Router を選択。

## 決定 2 — ストレージとメタデータ

- 決定: 受信アップロードおよび変換後の出力は AWS S3 を使用する。ジョブメタデータ（ConversionJob と VideoFile レコード）は DynamoDB を使用し、一時的出力には TTL を設定する。
- 理由: S3 は大容量ファイルにスケールし、Lambda/Batch ワークフローに自然に適合する。DynamoDB はサーバーレスで運用負荷が少なく、単純なジョブメタデータアクセスパターンに合致する。
- 検討した代替案: RDS/Postgres — MVP では運用コストが高くなるため見送り。

## 決定 3 — 認証

- 決定: Web アプリは公開（ユーザー認証なし）。アップロードとダウンロードは Next.js の Lambda Function URL サービスが生成する短時間有効なプリサインド S3 URL を使用する。S3 への直接アクセスはポリシーで制限し、ブラウザはプリサインド URL、Next.js Lambda と AWS Batch はそれぞれの IAM ロールを介してアクセスする。
- 理由: プリサインドアップロードは大きなファイルを Lambda 経由でルーティングする必要をなくし、MVP の導入を簡素化する。
- セキュリティ注記: 短時間有効なプリサインド URL を使い、アップロード後にファイルメタデータを検証する。機密扱いや有料フローが必要になった場合は認証を必須にする。

## 決定 4 — アップロードサイズ制限と SLA

- 決定: MVP のブラウザアップロード上限を 100 MB に設定する。100MB 以下のファイルについては検出を 5 秒以内に完了させる。変換 SLA はそのようなファイルの 90% を 5 分未満で完了することを目標とする。
- 理由: これらの境界は機能仕様の成功基準に沿い、MVP 時点で Batch リソース利用を合理的に保つ。
- 検討した代替案: 1–2GB など大きなサイズ — マルチパートアップロードや別 UX が必要なため MVP では見送り。

## 決定 5 — 対応ターゲットコーデック（MVP）

- 決定（MVP）: 初期ターゲットは H.264 (mp4)、VP9 (webm)、AV1 (webm) の少数に限定する。HEVC/H.265 はライセンスやデコーダー環境の懸念から後回しにする。
- 理由: H.264 は広範に互換性があり、VP9/AV1 はモダンなウェブ向けの選択肢を提供する。需要に応じて拡張可能。
- 検討した代替案: HEVC/H.265 を MVP に含める — ライセンスとデコーダーの可用性問題のため延期。

## 決定 6 — コンテナイメージと ECR

- 決定: ECR リポジトリを 2 つ作成する。
    - `codec-converter-web` — Next.js アプリのコンテナイメージ（CI からプッシュ）、Lambda コンテナイメージ作成に使用。
    - `codec-converter-batch` — 変換ジョブ用（ffmpeg 搭載）の Batch ワーカーイメージ。
- 理由: 関心事を分離し、権限の範囲を小さくして CI を単純化する。

## 決定 7 — Next.js が Batch ジョブを登録する方法

- 決定: Next.js の Lambda Function URL エンドポイントはプリサインドアップロード URL を生成し、ジョブ提出リクエストを受け付ける。アップロード後、Next.js Lambda は `SubmitJob`（AWS Batch）を呼び出し、ジョブ定義、環境変数（入力 S3 キー、出力 S3 プレフィックスなど）、一意のジョブ名／メタデータを渡す。変換進捗は Batch ジョブが DynamoDB を更新して報告する（Batch ジョブは DynamoDB 更新と S3 アクセスを許可する IAM ロールを想定）。Batch ジョブの実装言語は .NET、Node、Python いずれでもよく、コンテナには実際のコーデック操作のために `ffmpeg` が含まれている必要がある。
- 理由: Batch の `SubmitJob` を使うことで、コンテナ化された FFmpeg ワークロードを直接スケジューリングできる。

## 決定 8 — 可観測性と出力

- 決定: 変換ログは CloudWatch（Batch ジョブのログ）に保存する。ジョブステータスは DynamoDB に保存し、Next.js API エンドポイントで公開する。

- ダウンロード提供（S3 隠蔽）: エンドユーザーに S3 の存在を隠すため、Next.js 側でサーバーサイドのストリーミングダウンロードエンドポイント（例: `GET /download/{jobId}`）を実装する。エンドポイントは DynamoDB の `ConversionJob` を検証してから S3 のオブジェクトを `GetObject` でストリーミングし、HTTP ヘッダ `Content-Disposition: attachment; filename="..."` を付与してブラウザの標準ダウンロードを誘発する。

- ラショナル: これによりブラウザは Next.js ドメインからダウンロードしているように見え、S3 のホストや署名付き URL を露出しない。MVP では <=100MB 程度のファイルなら Lambda のストリーミングで問題ないが、ファイルが大きい／高頻度の場合は CloudFront 経由に移行することを検討する。

- セキュリティ注記: ダウンロード前にジョブのステータス、TTL、所有権／アクセス権を厳密にチェックすること。S3 キーは推測困難にし、ダウンロード可能な状態のファイルのみをサーバが流すようにする。

## 調査からの次のステップ

- `VideoFile`、`ConversionJob`、`Codec` エンティティと検証ルールを含む `data-model.md` を作成する。
- Next.js API エンドポイント（プリサインド生成、ジョブ提出、ステータス、ダウンロード）用の OpenAPI を `contracts/` に作成する。
- `web/nextjs/` と `batch/` ディレクトリをスキャフォールドし、初期の `Dockerfile` と CI パイプラインスニペットを作成して ECR にプッシュする。S3 バケットへのアクセスを Next.js Lambda ロールと Batch ロールに制限する IAM ロールとバケットポリシーのスニペット（プリサインド URL 使用のサンプルポリシー含む）を用意する。
